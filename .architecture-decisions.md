# Lengoali Curriculum Validator — Architecture Decisions

**Version:** 1.0  
**Status:** Implemented as a permanent, English-first validation subsystem  
**Decision date:** 2026-08-01

## Purpose

The Curriculum Validator is a repository-quality subsystem for inspecting curriculum data before future content expansion is accepted. It is deliberately separate from the learner-facing application. Its job is to inspect, analyze, measure, classify, and report. It never silently edits curriculum data.

The validator is a quality gate, not a content generator and not a cleanup script. A future contributor may add an explicit repair command later, but that would be a separate operation with a separate approval boundary.

## Architecture Review Before Implementation

### 1. Does it fit naturally?

Yes, with an offline tooling boundary. Lengoali is a pnpm workspace containing a React/TypeScript/Vite application and a `scripts` workspace that already supports TypeScript tooling through `tsx`. Curriculum data is assembled into `LanguagePack` objects by `curriculum-data.ts` and `curriculum-en.ts`, and the frontend loads those packs lazily through `loadLanguagePacks()`.

The natural integration point is therefore:

```text
curriculum source modules
        ↓ runtime import
validator normalizer
        ↓ internal domain model
independent validator modules
        ↓
statistics + quality scoring
        ↓
Markdown report
```

The validator observes the existing curriculum boundary. It does not become part of the React render tree or the browser bundle.

### 2. Will any requested feature conflict with the existing design?

Most requested capabilities are compatible. Three boundaries were required:

1. **The validator must not depend on LearnCenter.** LearnCenter is a consumer of curriculum data, not an authority over its validity. The validator imports the curriculum pack directly.
2. **CEFR analysis must not pretend to be official.** Version 1 uses transparent heuristic signals only and labels them as manual-review candidates. Official CEFR, Oxford, English Vocabulary Profile, frequency, and corpus datasets remain future adapters.
3. **Duplicate detection must not delete repeated words.** Existing curriculum intentionally reuses words across context and levels. The validator classifies occurrences and reports them.

No changes to curriculum files, `LearnCenter.tsx`, lessons, or the learning workflow are required.

### 3. Does it duplicate existing functionality?

The repository contains historical audit and generation work, including duplicate-unit cleanup and curriculum progress reports. Those are valuable historical records, but they are not a permanent, composable validation subsystem:

- historical audit scripts were task-specific;
- cleanup operations modified source data;
- progress reports describe past work rather than running against current source;
- TypeScript/build checks validate compilation, not content quality.

The new validator complements these controls instead of replacing them. It does not repeat the frontend's curriculum loading logic and does not duplicate LearnCenter behavior.

### 4. Is there a simpler maintainable solution?

Yes: one CLI entry point and small pure modules is simpler than introducing a UI dashboard, a backend service, a database, or a new curriculum representation. The chosen design keeps the existing TypeScript curriculum as the source of truth and uses a small internal normalized model for analysis.

### 5. Does it violate the project's architectural philosophy?

No. It reinforces modularity, separation of concerns, lazy frontend loading, and reusable curriculum architecture. The validator's domain contracts are independent from React and browser APIs. Its module interface is intentionally small:

```ts
name: string;
run(context: ValidationContext): ModuleResult;
```

### 6. Does it introduce unnecessary complexity?

The requested scope is broad, so some modularity is necessary. Complexity was kept bounded by:

- avoiding a framework;
- avoiding persistence;
- avoiding UI integration;
- avoiding automatic repair;
- sharing one normalizer and one module contract;
- keeping external dataset integration as a future adapter seam.

A future UI can consume report artifacts, but adding one now would expand scope without improving the first quality gate.

### 7. Are there better alternatives?

Alternatives considered:

| Alternative | Decision | Reason |
|---|---|---|
| Put validation in `LearnCenter` | Rejected | Couples quality logic to UI and runtime state. |
| Validate only serialized JSON | Rejected | The source of truth is assembled TypeScript, including enrichment and generated lessons. |
| Replace curriculum TypeScript with JSON | Rejected | Unnecessary migration and loss of the current source structure. |
| One monolithic validator file | Rejected | Harder to test, extend, and review. |
| Automatic deduplication | Rejected | Cannot infer pedagogical intent safely and violates non-destructive policy. |
| Official CEFR lookup now | Deferred | Requires dataset licensing, provenance, versioning, and language-specific mapping. |
| Backend validation service | Rejected for v1 | No need for network, persistence, or runtime validation in a static GitHub Pages app. |

## Existing Architecture and Integration Boundary

### Current project structure

- `artifacts/lengoali/src/learn-data.ts` defines the public curriculum types and lazy pack loader.
- `artifacts/lengoali/src/curriculum-data.ts` assembles the Finnish pack.
- `artifacts/lengoali/src/curriculum-en.ts` assembles the English pack from base, part, and enrichment modules.
- `artifacts/lengoali/src/LearnCenter.tsx` consumes resolved packs for the learner experience.
- `scripts/` is the workspace for repository tooling and already provides `tsx`.
- `.github/workflows/pages.yml` builds the Vite application and deploys static output to GitHub Pages.

The validator lives under `scripts/src/curriculum-validator/`. The production application does not import it.

### Current data flow

```text
curriculum-en.ts + its source modules
        ↓
ENGLISH_PACK: LanguagePack
        ↓
loadLanguagePacks() (frontend, lazy)
        ↓
LearnCenter and learning features
```

The validator adds an independent offline branch:

```text
ENGLISH_PACK (runtime import by CLI)
        ↓
normalizePack()
        ↓
ValidationContext
        ↓
structure / vocabulary / duplicate / metadata
        ↓
topic / CEFR / statistics
        ↓
quality scores + Markdown report
```

The two branches share source data but not UI responsibilities.

## Module Responsibilities

### Domain contracts

`domain.ts` defines CEFR values, normalized vocabulary records, pack/level/unit/lesson contracts, issue severity, module results, statistics, quality scores, and the validator run. These contracts are internal to the validator and deliberately avoid importing frontend types at compile time.

### Normalizer

`normalize.ts` accepts unknown runtime data and creates a stable internal representation. It trims strings, safely handles missing arrays, records source paths, and preserves raw structural objects for future modules. It does not mutate the input.

### Structure Validator

Checks pack identity, CEFR values, expected levels, duplicate level IDs, duplicate unit IDs within a level, duplicate lesson IDs within a unit, missing collections, and broken review-item references. Unit IDs are intentionally local to each CEFR level; `A1/u1` and `B2/u1` are different valid identities.

### Vocabulary Validator

Checks empty words and translations and reports distribution metrics. It does not decide whether a word is pedagogically appropriate by itself.

### Duplicate Validator

Groups normalized vocabulary by word and classifies repeated records using location, level spread, and part of speech. Version 1 categories include intentional review, contextual reuse, different part of speech, and suspicious duplicate. Different meaning and subtle context remain human-review concerns.

### Metadata Validator

Measures completion for translation, translation language, part of speech, definition, IPA, audio, example, example translation, synonyms, antonyms, collocations, word family, tags, and category. Required-field warnings are intentionally narrower than completeness measurements so legacy or optional fields remain visible without being falsely treated as fatal.

### Topic Coverage Validator

Uses transparent keyword families against unit titles, descriptions, categories, tags, and vocabulary context. It reports covered, weak, and missing domains by pack and CEFR level. Keyword matching is a directional baseline, not semantic classification.

### CEFR Validator

Produces heuristic estimates based on word shape and flags large placement gaps for manual review. It explicitly does not claim official CEFR verification. This keeps the architecture ready for an external dataset without hard-coding a future provider.

### Statistics Generator

Calculates records, unique vocabulary, duplicate ratio, level/unit distribution, lesson/unit counts, average lesson size, average unit size, and average vocabulary growth.

### Quality Scoring

Computes scores from measurable outputs rather than editorial intuition. Scores cover architecture, curriculum consistency, vocabulary, metadata, topic coverage, lesson/unit consistency, duplicate quality, and overall quality. They are diagnostic indicators, not certification.

### Report Generator

Renders the validation run as `.curriculum-validation-report.md` in the repository root. It includes executive summary, architecture summary, module findings, errors, warnings, statistics, duplicate analysis, metadata completion, topic coverage, CEFR analysis, quality scores, and recommendations.

## Non-Destructive Policy

The validator:

- never writes to curriculum source files;
- never removes duplicates;
- never changes CEFR assignments;
- never enriches translations or metadata;
- never changes lessons or units;
- never changes LearnCenter or UI state;
- writes only the requested report artifact when run.

A future repair workflow must be a separate, explicit command with a dry run, reviewable diff, and clear opt-in.

## Extension Rules

### Adding Finnish or another language

Do not copy validator modules. Pass another pack loader to `validatePack`, or add a pack-selection layer that supplies a normalized pack to the same module list. The domain model already represents target language and explanation languages as data.

A future multi-pack CLI should:

1. load a named pack;
2. normalize it;
3. run the same modules;
4. write a language-scoped report;
5. retain pack identity in every issue path and metric.

### Adding official CEFR or frequency data

Introduce a data provider interface, for example:

```ts
interface VocabularyEvidenceProvider {
  lookup(word: string, language: string): Promise<{
    cefr?: string;
    frequencyRank?: number;
    source: string;
  } | null>;
}
```

The current CEFR module should become a fallback strategy, not be deleted. External evidence must include source, version, language, and licensing/provenance metadata.

### Adding curated duplicate decisions

Use a separate decision registry keyed by normalized word and context. Never encode exceptions as silent conditionals inside the duplicate detector. The report should show whether a classification came from a rule, a curated decision, or an external evidence provider.

### Adding tests

Prefer pure fixture tests for each module:

- valid minimal pack;
- missing level/unit/lesson;
- local repeated unit IDs across different levels;
- intentional repeated vocabulary across levels;
- suspicious same-lesson duplicate;
- missing metadata;
- missing topic;
- CEFR heuristic review candidate;
- report rendering.

## Quality Gate Policy

The intended future workflow is:

1. author curriculum changes;
2. run `pnpm --filter @workspace/scripts run validate:curriculum`;
3. inspect `.curriculum-validation-report.md`;
4. resolve structural errors;
5. review warnings and duplicate classifications;
6. run workspace typecheck and production build;
7. review the diff to ensure source changes are intentional;
8. accept the curriculum change only after the quality evidence is reviewed.

Version 1 does not yet enforce a CI failure threshold for every warning. That is intentional: the existing curriculum contains optional metadata and heuristic findings that require policy decisions before becoming hard gates.

## Known Limitations

- English is the current CLI scope; Finnish reuse is architecturally prepared but not the default report.
- Topic coverage is keyword-based.
- CEFR classification is heuristic, not official.
- Duplicate intent cannot be inferred perfectly from text alone.
- Audio is measured as metadata but not verified remotely.
- Translation correctness is not semantically evaluated.
- No JSON report or fixture test suite is included in v1.
- The report is generated on demand rather than automatically on every pull request.

These are documented limitations, not hidden promises.

## Why This Design Should Continue

This design keeps the frontend focused on learning and the scripts workspace focused on repository quality. It permits independent growth of curriculum data, validator logic, and future evidence providers. It is small enough to understand, explicit enough to audit, and non-destructive enough to run before every expansion. Most importantly, it turns curriculum quality into a repeatable engineering activity without changing the learning product itself.
