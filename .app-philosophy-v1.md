## 1. Project Vision

### What Lengoali is

Lengoali (legacy internal name "Lingolali", still present in some comments and docs) is a **free, browser-based, multilingual language-learning platform**. It is a static single-page application (React + Vite + TypeScript) deployed to **GitHub Pages** — there is no server required for the core learning loop.

The product has two complementary learning surfaces:

1. **Translation-first reading** — the user pastes (or reads) any text in any language, taps any word, and gets an instant translation, definition, etymology, synonyms, and more. Words can be saved to a personal library.
2. **Structured CEFR curriculum** — two full language packs (Finnish and English) organized into CEFR levels A0–C2, with units, two lessons per unit, vocabulary, grammar, dialogue, reading passages, exercises, and quizzes.

Both surfaces feed a **personal vocabulary system** with flashcards, quizzes, daily goals, streaks, and a spaced-repetition (SM-2 style) review engine — all persisted in the browser's `localStorage` (no account required).

### Long-term goals

- Grow the English curriculum toward **5,000+ quality vocabulary entries** with rich metadata (IPA, definitions, synonyms, antonyms, collocations, word families, tags, categories).
- Keep the curriculum architecture **language-agnostic** so new language packs can be added by following the same conventions.
- Maintain a **fast, zero-backend, zero-config** experience: open the page, start learning.
- Introduce **quality gates** (a curriculum validator) so content volume never outpaces content quality.

### Educational philosophy

- **Translation-first reading.** Real language acquisition happens through comprehensible input. The reader makes any authentic text immediately comprehensible (tap-to-translate), which lowers the barrier to reading real content.
- **Spaced repetition.** The review engine (`vocabulary-data.ts`) models each word with an ease factor, interval, and repetition count (SM-2 style), so weak words reappear sooner.
- **CEFR progression.** Structured content is scaffolded from A0 (Foundations) to C2 (near-native), with level-appropriate vocabulary, grammar, and reading.
- **Original content.** Curriculum material is written from scratch; the project explicitly avoids copying from Duolingo, Babbel, Busuu, Memrise, LingQ, or textbooks.
- **Multiple explanations.** The English pack supports explanation languages (Arabic, Spanish, French, Finnish); learners pick the language they understand best.

### Target users

- Self-directed language learners (Finnish and English as target languages today).
- Learners whose first language is Arabic, Spanish, French, Finnish, or English (the five UI languages).
- Users who want to learn by reading real text (the reader) and by following a structured course (the curriculum).
- Arabic-speaking learners are a primary audience historically — several legacy curriculum files contain Arabic translations and the UI is fully localized in Arabic (RTL included).

### Why this architecture was chosen

- **Static hosting is free and zero-ops.** GitHub Pages + a pure client-side app means no servers, no databases, no API keys for the core flow.
- **Client-side translation avoids paid APIs.** The app calls Google's unofficial web endpoints directly; no developer API key is needed.
- **A monorepo lets the product evolve separately from shared libraries.** The workspace (`pnpm-workspace.yaml`) holds the app, a scaffold API server, shared libraries, and scripts.
- **Typed curriculum data keeps content honest.** Every word, lesson, and unit conforms to TypeScript contracts, so structural errors fail at compile time instead of at runtime.

### Problems the project solves

- "I know grammar but can't read real texts" → tap-to-translate reader.
- "I learn words but forget them" → spaced-repetition review + flashcards + quizzes.
- "Language apps are locked behind subscriptions or limited languages" → free, open, self-hostable, 40+ languages via Google translation.
- "Curriculum content is often a black box" → the entire curriculum is plain, versioned, inspectable TypeScript data in the repository.

## 2. Development Philosophy

### Modularity

The codebase is deliberately split by *layer* (types → content → builders → catalog → UI) and by *language* (Finnish vs English) and by *content batch* (part files). Adding a new unit batch means adding one new file — never editing the app logic.

### Scalability

The curriculum has already grown from a handful of units to **hundreds of units across 14 level-arrays** (7 per language). The `mergeAdditionalUnits(...)` pattern lets content keep growing in independent files without touching existing ones. `buildVocabularyCatalog` explicitly states it "deliberately has no maximum size", including catalogs beyond 5,000 entries.

### Maintainability

- Strict TypeScript contracts (`learn-data.ts`) are the single source of truth for data shape.
- Generated files are clearly marked (`// This file is generated; do not edit manually.`) so agents don't hand-edit them.
- Small, single-purpose files: each `curriculum-*-partN.ts` is one content batch.
- A repair layer (`curriculum-en-clean.ts`) encodes *how to fix* contaminated records, making fixes reproducible rather than one-off.

### Simplicity

- **No URL router** for the core flow: the app uses tab state and drill-down state (`App.tsx` holds `tab`, `LearnCenter` holds level/unit/lesson state). `wouter` is installed but unused in the current app code.
- **No backend** for the learning loop: everything the learner does is computed client-side and persisted to `localStorage`.
- Straightforward, dependency-light choices (Google endpoints, Web Speech API, `localStorage`) over heavier infrastructure.

### Separation of concerns

| Concern | File(s) |
|---|---|
| Data model / types | `learn-data.ts` |
| Curriculum content + builders | `curriculum-data*.ts`, `curriculum-en*.ts` |
| Repair / normalization | `curriculum-en-clean.ts` |
| Metadata enrichment | `curriculum-en-enrichment.ts` |
| Vocabulary catalog + SRS | `vocabulary-data.ts` |
| Curriculum UI | `LearnCenter.tsx`, `components/LessonNavigation.tsx` |
| SRS UI | `components/LearnWordVocab.tsx` |
| Reader / quiz / flashcards / saved words | `App.tsx` |
| Shared UI primitives | `components/ui/*` (shadcn/ui) |

### Lazy loading

`loadLanguagePacks()` in `learn-data.ts` uses **dynamic `import()`** for both packs:

```ts
const [{ FINNISH_PACK }, { ENGLISH_PACK }] = await Promise.all([
  import("./curriculum-data"),
  import("./curriculum-en"),
]);
```

Vite turns each curriculum file into a separate chunk, so the **initial bundle stays around 310 kB** while the (much larger) curriculum chunks load only when the learner enters the curriculum.

### Progressive enhancement

- **TTS**: uses the browser's Web Speech API (`speechSynthesis`) when available, and falls back to an `<audio>` element streaming Google's `translate_tts` endpoint otherwise (including a no-start watchdog timer).
- **Translation**: rich Google endpoint calls (`dt=t, bd, ss, rm, ex, ld`) with graceful failure → empty results and UI copy like "The word service is unavailable right now."
- **Theme & RTL**: dark/light themes and LTR/RTL layout are handled entirely client-side with inline theme objects.

### Reusable curriculum architecture

Both Finnish and English packs are built by the *same* builder functions (`chunk`, `splitReading`, `buildLesson`, `buildUnit`, `buildLevel`, `buildLanguagePack`), defined once per pack file (duplicated to avoid circular imports). Adding a new language = new content files + one export wired into `loadLanguagePacks`.

## 3. High-Level Architecture

```
┌────────────────────────────── App.tsx (shell) ──────────────────────────────┐
│  theme · UI i18n (en/ar/fi/es/fr) · language registry (40+) · TTS helpers   │
│  tabs: input | reader | learn | words | saved | quiz                         │
└──────┬───────────────────┬──────────────────────┬───────────────────────────┘
       │                   │                      │
   Reader/Quiz/        LearnCenter             LearnWordVocab
   Saved/Flashcards   (curriculum browser)    (SRS review)
       │                   │                      │
       └───────┐           │                      │
          loadLanguagePacks() (lazy import)       │
       ┌───────▼──────────────────────┐           │
       │     learn-data.ts (types)    │           │
       │  curriculum-data.ts (FI)     │           │
       │  curriculum-en.ts (EN)       │◄──────┬───┘ buildVocabularyCatalog()
       │  + part files + clean + enrich│       │
       └──────────────────────────────┘       │
                                   vocabulary-data.ts
                                   (catalog + SRS + localStorage)
```

### Subsystems

- **App shell (`App.tsx`)** — the only top-level component (`main.tsx` → `<App/>`). Owns theme, UI language, language registry, TTS, source/target languages, and the six tabs. Large file (~3,500 lines) — see Technical Debt.
- **Reader** — splits pasted text into paragraphs, lets the user tap any word, shows a translation sheet with back-translation, definitions, synonyms, and POS-colored highlighting.
- **Quiz** — two quiz experiences: per-lesson generated quizzes inside `LearnCenter`, and a saved-words quiz tab in `App.tsx` (typing, multiple-choice, reverse modes; sound effects; accuracy; wrong-word review).
- **Flashcards** — from the saved-word library (`Flashcard` component) and per-lesson word pairs (`lesson.flashcards`).
- **Saved words** — `lengoali_saved_v4` in `localStorage`; editable translations, notes, filters (review/edited), sorting, copy-all, CSV-style export/delete.
- **LearnCenter (`LearnCenter.tsx`)** — the curriculum browser: pack → level → unit → lesson. Onboarding flow (target language + native language), progress bars, lesson view with vocabulary cards, grammar, reading, exercises, quiz, and save-word actions.
- **Curriculum Engine** — `learn-data.ts` types + `curriculum-*.ts` seed data and builder functions (Section 5).
- **Vocabulary System** — `vocabulary-data.ts`: flattens any pack into a stable catalog of `CurriculumVocabularyWord` records; SM-2-style review state machine; `lengoali_vocabulary_progress_v1`.
- **Translation** — direct calls to Google's unofficial web endpoint (`translate.googleapis.com/translate_a/single?client=gtx`), with `dt` options for translation, definitions, synonyms, etymology, romanization, and example extraction. **No API key, no backend.**
- **Persistence** — `localStorage` only (keys listed in Section 9). No IndexedDB, no server sync.
- **Settings** — theme, UI language, sound on/off, source language, ordered target languages.
- **Deployment** — GitHub Pages via `.github/workflows/pages.yml`; static output in `dist/public`.

### How the subsystems communicate

- **Props**: `App` passes `t` (theme), `s` (i18n strings), language packs, and callbacks into `LearnCenter`, `LearnWordVocab`, and the tab components.
- **Shared modules**: `LearnCenter` and `LearnWordVocab` both consume `learn-data` types and `vocabulary-data` helpers directly.
- **Shared storage**: lesson progress (`lengoali_learn_progress_v2`), vocabulary review state (`lengoali_vocabulary_progress_v1`), saved words (`lengoali_saved_v4`), streaks/daily goals (`lengoali_streak_v1`, `lengoali_daily_goal_v1`).
- **No event bus / global store**: React state + props + `localStorage` is the entire communication graph — deliberately simple.

```
├── lib/                          # Shared workspace libraries
│   ├── db/                       # 🟡 Drizzle + Postgres (schema dir empty; scaffold)

│   └── api-spec/                 # OpenAPI spec + Orval codegen (health schema only)
├── scripts/                      # Workspace scripts (hello.ts; post-merge.sh)
├── docs/                         # Reports (curriculum progress, branding audit)

```

### Why files are separated this way

- **`artifacts/` vs `lib/`**: runnable apps are kept apart from libraries so each can be versioned, built, and deployed independently. The app is the only artifact deployed to Pages.
- **Per-batch curriculum files (`part3`, `part4`, …)**: keeping each content batch in its own file makes git history readable, avoids giant merge conflicts, and lets a generator script append to exactly one file. The "more" files (`curriculum-*-more.ts`, ~16.5k lines) hold the legacy generated batches.
- **`components/ui/`**: shadcn/ui primitives are vendored separately from product components (`LearnWordVocab`, `LessonNavigation`), so product code never mixes with boilerplate.
- **`src/data/types.ts`** holds *legacy* curriculum types (`w/en/ar` style) used by older data; the *current* model lives in `learn-data.ts`. Both coexist; new code should use `learn-data.ts`.
- **`docs/`** keeps narrative reports (progress, branding audit) out of source so they never affect the build.

## 5. Curriculum Architecture

### The CEFR skeleton

- **7 levels:** A0, A1, A2, B1, B2, C1, C2 — defined as the `Level.cefr` union in `learn-data.ts`.
- **Level → units:** each level has 3 base units (`u1`–`u3`, hand-written in the pack files) plus additional units (`u4`…`u56`) merged from part files.
- **Unit → lessons:** every unit becomes **exactly 2 lessons** ("Part 1", "Part 2") via `buildUnit` → `buildLesson`.

### Unit IDs are local to each CEFR level — by design

`u54` exists in **every** level (A0…C2), each with **different** content (e.g., A0 "Seasons" vs B2 "Cultural Trends" vs C2 "Philosophical Concepts"). The identity of a unit is the **pair (level, unitId)**, not the bare id. This is intentional:

- Generation scripts and part files can number units per level without a global registry.
- Enrichment is keyed the same way: `ENGLISH_UNIT_ENRICHMENTS[level][unit.id]`.

**Trade-off:** the UI must always render the level alongside the unit (it does), and cross-level lookups must key on the pair.

### How a lesson is generated (`buildLesson`)

Given a unit seed (`words`, `phrases`, `dialogue`, `reading`) and its level seed (`grammar`, `pronunciationTips`):

- **Words:** `chunk(words, 2)` → each lesson gets half the unit's words.
- **Reading:** `splitReading(...)` splits the passage by sentences, giving each lesson half.
- **Phrases & dialogue:** likewise chunked in 2.
- **Grammar:** assigned round-robin from the level's grammar list: `grammarIndex = (unitIndex * 2 + lessonIndex) % grammar.length`.
- **Pronunciation tip:** round-robin from the level's tips.
- **Exercises** (generated):
  - lesson 1: word→translation **match**; reading-comprehension **choice**.
  - lesson 2: **fill-in-the-blank** (from word examples, with the target word blanked), phrase **match**, reading **choice**.
- **Quiz** (generated): one multiple-choice "What does X mean?" per word + one grammar-focus question.
- **Flashcards:** `front: word, back: translation` for each lesson word.
- **reviewItems:** the lesson's words (used for review workflows).
- **estimatedDuration:** computed from word count.

### Why units are split into lessons

1. **Pacing:** two short sessions are less intimidating and map to realistic study sessions.
2. **Progression:** Part 1 = recognize/understand; Part 2 = apply/use (different objectives and exercise mix).
3. **Reuse:** one unit seed yields two distinct lessons, so authoring content once produces more teaching material.

### The assembly pipeline

```
learn-data.ts (types)
   │
   ├─ curriculum-data.ts      FINNISH_LEVELS (u1–u3/level)      + ADDITIONAL_FI_UNITS
   │     buildLanguagePack(…, FINNISH_LEVELS, ADDITIONAL_FI_UNITS, FINNISH_MANUAL_A0)
   │       ADDITIONAL_FI_UNITS = merge(data-more u4–u27, part3…part8)
   │
   └─ curriculum-en.ts        ENGLISH_LEVELS (u1–u3/level)      + ADDITIONAL_EN_UNITS
         buildLanguagePack(…, ENGLISH_LEVELS, ADDITIONAL_EN_UNITS, ENGLISH_MANUAL_A0)
           ADDITIONAL_EN_UNITS = merge(
             clean(u4–u27 repaired from Finnish source),
             part3…part17 (u28+))
           then enrichEnglishAdditionalUnits() appends enrichment words
```

Key functions:

- `mergeAdditionalUnits(...sources)` — concatenates per-level unit arrays from many files.
- `enrichEnglishAdditionalUnits(...)` — appends `ENGLISH_UNIT_ENRICHMENTS[level][unit.id]` words into matching units (English only).
- `buildLanguagePack(...)` — builds all levels, then:
  - sets the **default `translationLang`**: `"es"` for the English pack, `"en"` for Finnish (each unit word gets a translation language unless it already declares one),
  - **replaces level A0 unit 1 with a hand-written manual unit** (`ENGLISH_MANUAL_A0` / `FINNISH_MANUAL_A0` from `curriculum-manual-a0.ts`) to preserve the original "Welcome & Numbers" lessons.
- `curriculum-en-clean.ts` — the **repair layer** (Section 10): rebuilds English additional units from the bilingual Finnish source, keeping clean legacy English records and *inverting* contaminated ones (Finnish text that leaked into the English pack), then infers `translationLang` from script detection (Arabic / Finnish / Spanish).

### Grammar

Each level owns a hand-written `grammar: GrammarItem[]` (6 items per level in the English pack, from "The verb 'be'" at A0 to "Translation competence" at C2) plus `pronunciationTips[]`. Lessons borrow them round-robin, so grammar is level-appropriate and repeated across units for reinforcement.

### Dialogue, reading, phrases

Every unit seed contains a 3–4 line dialogue, a short reading passage (with translation), and useful phrases — all original. These are split across the two lessons and also feed the reading-comprehension exercise.

### Review & quizzes

- Per-lesson `quiz` (generated) — comprehension of the lesson's own words.
- `flashcards` — per-lesson pairs for quick study.
- `reviewItems` — plain word list for review workflows.
- The **separate SRS system** (`vocabulary-data.ts`) tracks mastery of *catalog* entries independently of lesson structure (Section 6).

## 6. Vocabulary Philosophy

### Organization

Vocabulary is defined **inside units** (`words: VocabularyItem[]`), then **flattened once** into a stable catalog by `buildVocabularyCatalog(pack)`:

```
CurriculumVocabularyWord {
  id: `${targetLang}:${level}:${unitId}:${slug(word)}`,
  word, language, level, unitId, unitTitle, lessonId, lessonTitle,
  category (= item.category || unit.title),
  ipa, audioUrl, pos, nativeMeaning, nativeMeaningLang,
  definition, example, exampleTranslation,
  synonyms, antonyms, collocations, wordFamily,
  cefr, tags (= item.tags || derived from unit title)
}
```

The catalog is the single source for the SRS screens; it is **derived** (never hand-maintained), so adding units automatically expands it.

### How words are selected

- **Manually curated, topic-driven.** Units are written around everyday, professional, academic, and philosophical topics that progress with CEFR level (A0 food/colors/numbers → C2 discourse analysis/metaphysics).
- **Not frequency-list driven today.** There is currently **no** external corpus, frequency list, or CEFR word list (e.g., NGSL, AWL, CEFR vocabulary profiles) referenced anywhere in the repo. Selection is expert/manual. 🟡 (A future validator could add frequency-based sanity checks.)

### Why repetition exists

Repetition is **intentional** and categorized:

- **New vocabulary** — first encounter in a unit.
- **Review** — the same word re-entered in another unit/level for reinforcement (e.g., "investment" in both economy and global-finance contexts).
- **Reuse** — words reused inside generated exercises/quizzes/flashcards within the same lesson.
- **Contextual repetition** — the same word in different contexts (reading passage, dialogue, examples) deepens acquisition.
- **Future enrichment** — `curriculum-en-enrichment.ts` adds metadata-rich entries to existing units without renaming/restructuring them.

### Deduplication policy (current)

- `buildVocabularyCatalog` deduplicates **within a unit**: key = `level:unitId:slug(word)`, first occurrence wins. The comment states the intent: *"Preserve the same word when it is intentionally taught in another unit, while still removing duplicate entries within one unit."*
- Legacy history: duplicate `u12`/`u13` units (whole units, not words) were removed by a cleanup script in a previous session.
- There is **no automated cross-level or cross-unit duplicate detector** beyond the catalog key. 🟡

### How future vocabulary should be added

1. **Preferred:** append a new part file (e.g., `curriculum-en-part18.ts`) exporting `ADDITIONAL_EN_PART18_UNITS: Record<string, UnitSeed[]>` and wire it into `mergeAdditionalUnits` in `curriculum-en.ts`. The catalog and lessons update automatically.
2. **Enrich existing units:** add entries under `ENGLISH_UNIT_ENRICHMENTS[level][unitId]` in `curriculum-en-enrichment.ts` (rich metadata: IPA, definition, synonyms, collocations, word family, tags, category).
3. **Rules:** 8+ words per unit, each with POS, example, and translation; 4 useful phrases; a 4-line dialogue; one reading passage; original content only; keep translations' language explicit via `translationLang`.

## 7. Metadata Philosophy

Every field on `VocabularyItem` (from `learn-data.ts`) and its role:

| Field | Purpose | Required today? | Notes |
|---|---|---|---|
| `word` | Target-language headword | ✅ required (type-level) | The teaching unit. |
| `translation` | Meaning in the explanation language | ✅ required (type-level) | |
| `translationLang` | Which language `translation` is in | 🟡 optional, **defaulted by the builder** | English pack defaults to `"es"`, Finnish to `"en"`; `curriculum-en-clean` infers `ar`/`fi`/`es` from script detection. |
| `pos` | Part of speech | 🟡 optional but near-universal | Drives POS coloring in the reader. |
| `example` | Example sentence (target language) | 🟡 optional | Feeds fill-in-blank exercises. |
| `exampleTranslation` | Translation of the example | 🟡 optional | |
| `ipa` | Pronunciation | 🟡 optional | Populated in enrichment + newer part files; sparse in base units. |
| `audioUrl` | Audio clip URL | 🟡 optional | Declared in types/catalog; effectively unused in the current app (TTS is synthetic). |
| `definition` | Monolingual definition | 🟡 optional | Rich in enrichment; sparse elsewhere. |
| `synonyms` / `antonyms` | Lexical relations | 🟡 optional (string OR string[]) | `cleanList` normalizes both shapes in the catalog. |
| `collocations` | Common word partners | 🟡 optional | Rich in enrichment. |
| `wordFamily` | Morphological family | 🟡 optional | Rich in enrichment. |
| `tags` | Topic tags | 🟡 optional (string OR string[]) | Catalog falls back to tags derived from unit title. |
| `category` | Semantic category | 🟡 optional | Catalog falls back to unit title. |

**Philosophy:** the type contract is *permissive* (almost everything optional) so that all content generations remain valid; **enrichment is where rich metadata lives**. The catalog (`vocabulary-data.ts`) then *normalizes* whatever exists (lists, fallbacks, `cleanList`) into a consistent shape for the UI. The consequence: metadata completeness is **not enforced** — a validator (Section 11) is the planned enforcement layer.

## 9. Runtime Behaviour

### Lazy loading & bundle size

- Curriculum packs are dynamic imports; the **initial JS stays ~310 kB** while curriculum chunks grow with content (per the curriculum progress report).
- `vite.config.ts` requires `PORT` and `BASE_PATH` env vars at build time (fails fast if missing) — `BASE_PATH` becomes Vite's `base` so assets resolve under `/Legacy-Code-Update/` on Pages.
- Build output goes to `dist/public` (matching the Pages artifact path).

### Caching

- Standard Vite content-hashed asset filenames → long-term browser caching of immutable assets.
- No service worker / PWA today. 🟡

### State persistence (all `localStorage`)

| Key | Purpose |
|---|---|
| `lengoali_saved_v4` | Saved word library (migrates from v3) |
| `lengoali_quiz_prefs_v1` | Quiz modes/preferences |
| `lengoali_daily_goal_v1` | Daily goal progress `{date, goal, learned}` |
| `lengoali_streak_v1` | Day streak `{lastDate, days}` |
| `lengoali_sound_v1` | Sound on/off |
| `lengoali_theme` | Dark/light |
| `lengoali_ui_lang` | UI language |
| `lengoali_source_lang` | Reader source language |
| `lengoali_target_langs` | Ordered translation targets |
| `lengoali_learn_progress_v2` | Lesson completion map (per lesson: last location + completed ids) |
| `lengoali_vocabulary_progress_v1` | SRS state per catalog word id |
| `lengoali-learn-onboarding` | Onboarding target/native language |

All writes are wrapped in try/catch (storage can be unavailable, e.g., private mode).

### Navigation

- Tab state in `App` (`input | reader | learn | words | saved | quiz`) — no URL routing for the core flow.
- `LearnCenter` keeps its own drill-down state (selected pack/level/unit/lesson) and resumes from saved lesson progress.

### Translation & TTS at runtime

- Translation: `fetch(buildGoogleUrl(text, sl, tl, dts))` against `translate.googleapis.com/translate_a/single?client=gtx` with `dt=t/bd/ss/rm/ex/ld`. Responses are parsed for translation, back-translation, POS, definitions, synonyms, romanization, and examples. **Unofficial endpoint — fragile to Google changes; no key required.** 🟡
- TTS: Web Speech API first, Google `translate_tts` audio fallback (chunked ≤190 chars), with a fallback watchdog if synthesis doesn't start within 800 ms.

## 10. Quality Assurance Philosophy

### What exists today

| Control | Status | Evidence |
|---|---|---|
| TypeScript strict typecheck | ✅ | `tsconfig.base.json` (strict: `strictNullChecks`, `noImplicitAny`, `noImplicitReturns`, …), root `pnpm run typecheck` runs `tsc --build` for libs + per-package typechecks. CI builds only the app, but the workspace typecheck covers everything. |
| Production build validation | ✅ | `vite build` in CI (`.github/workflows/pages.yml`) and locally (`PORT`/`BASE_PATH` env required). |
| Structural repair of curriculum data | ✅ | `curriculum-en-clean.ts` — script-aware *repair* pipeline that detects contaminated English records (Finnish characters, identical word/translation/example) and rebuilds them from the bilingual Finnish source; also infers `translationLang`. |
| Within-unit duplicate removal | ✅ | `buildVocabularyCatalog` dedupes by `level:unitId:slug(word)`. |
| Legacy duplicate-unit cleanup | ✅ (historical) | `u12`/`u13` duplicate units removed by a one-off script (commit `68d9d77`). |
| Duplicate-ID detection per level | 🟡 | Only done ad-hoc with Python parsing scripts during generation sessions (documented in `docs/CURRICULUM_PROGRESS_REPORT.md`); **no committed validator**. |
| CEFR verification | 🟡 | Levels are typed (`"A0"…"C2"`), and content was authored to progress with level, but there is **no automated check** that a word belongs to its level. |
| Spelling validation | ❌ | None (no dictionary/aspell integration). |
| Translation validation | 🟡 | Heuristic only: `isContaminatedWord` + script detection in `curriculum-en-clean`; no semantic check. |
| Metadata completeness checks | ❌ | No check that words carry IPA/definition/synonyms/etc. |
| Topic balance / domain coverage | 🟡 | Topics are curated per level by hand; **no automated coverage matrix**. |
| Progression checking | 🟡 | Manual (round-robin grammar, level-appropriate topics); no automated difficulty metric. |
| Curriculum statistics | 🟡 | Reported narratively in `docs/CURRICULUM_PROGRESS_REPORT.md` (word counts per pack); no committed reporting tool. |
| Unit/lesson consistency | 🟡 | Enforced structurally by `buildLesson` (uniform shape), verified by typecheck; content-level consistency is manual. |
| Tests (unit/integration) | ❌ | No test runner or test files exist in the repository. |

### Current limitations

- **No committed validator.** Every audit so far (duplicate ids, field completeness) was done with throwaway Python scripts during authoring sessions, then discarded.
- **No CI quality gate** beyond "it compiles and builds."
- **Metadata is optional** in the type system, so completeness depends on author discipline.
- **No automated duplicate detection across units/levels** (only within a unit).
- **Manual translation risk** — translations are authored by hand (or inferred by script detection); errors are only caught by review.
- **Unofficial translation endpoint** can break without notice; there is no fallback provider.

## 11. Future Quality Architecture (recommended, not implemented)

A **Curriculum Validator** should become the central quality gate. Recommended design — entirely additive:

### Stage 0 — Loader

Parse/import the *effective* curriculum exactly as the app sees it (import `ENGLISH_PACK`/`FINNISH_PACK` from the built modules, or walk the seed files). Validating the **final built model** (after merge/clean/enrichment) is what matters, because that is what learners see.

### Stage 1 — Structural checks (cheap, fail-fast)

- Every level is A0–C2; every unit id is unique **within its level**; every lesson has a unique id.
- Every lesson has ≥1 vocabulary item, ≥1 exercise, ≥1 quiz question, a reading text.
- No empty/whitespace-only strings for `word`, `translation`, `title`, `description`.

### Stage 2 — Duplicate detection

- **Within unit:** exact and normalized (slug, case, whitespace) duplicates of `word`.
- **Across units/levels:** report intentionally-repeated words (same word, different context) separately from accidental duplicates; recommend allowing repeats **only** when context/meaning differs. Output a report, not a hard failure.

### Stage 3 — Metadata completeness

- Compute coverage per field (`ipa`, `definition`, `example`, `exampleTranslation`, `synonyms`, `antonyms`, `collocations`, `wordFamily`, `tags`, `category`) per level and per unit.
- Gate on *goals* (e.g., "≥90% of words have IPA + definition") rather than 100% to avoid blocking incremental growth.

### Stage 4 — Translation & language sanity

- Script/character detection: `translation` and `exampleTranslation` must not be in the **target** language (this is exactly the contamination class `curriculum-en-clean` repairs).
- `translationLang` consistency: declared language must match detected script (Arabic/Finnish/Spanish/English heuristics).
- Optional external dictionary spot-checks for translations of high-frequency words.

### Stage 5 — CEFR & difficulty sanity

- Word-frequency sanity: top-frequency words shouldn't appear first at C1+; rare/academic words shouldn't appear at A0. Requires an external frequency list (💡 e.g., NGSL for English).
- Grammar ordering check: grammar items are level-appropriate (manual rubric first; later an AI rubric).

### Stage 6 — Topic coverage matrix

- Tag every word/unit with a domain (Family, Food, Travel, Health, Work, Business, Education, Technology, Government, Science, Nature, Communication…).
- Report coverage per level and flag empty cells (e.g., "A1 has no Health words").

### Stage 7 — Statistics & report

- Per level: unit count, word count, unique-word count, phrase/dialogue/reading counts, metadata coverage %, top repeated words.
- A single `report` output that reflects the **effective** curriculum after all layers.

### Stage 8 — CI integration

- Run Stages 1–2 (and 3–4 as warnings) in GitHub Actions on every push; block merge on structural errors. Everything additive to `package.json` scripts + one workflow job.

### Suggested tooling

- A TypeScript script run via `tsx` (already a workspace dependency) in `scripts/` (e.g., `scripts/validate-curriculum.ts`), so it can import the real modules with full typing.
- Python continues to be fine for one-off generation, but the committed validator should live in the workspace it validates.

## 12. Development Rules

### Adding new curriculum (units)

1. **Never edit generated files** (`curriculum-*-more.ts`). They are marked "generated; do not edit manually."
2. Create a new part file (e.g., `curriculum-en-part18.ts`) with `export const ADDITIONAL_EN_PART18_UNITS: Record<string, UnitSeed[]>`.
3. Import and add it to `mergeAdditionalUnits(...)` in `curriculum-en.ts` (or `curriculum-data.ts` for Finnish).
4. Content per unit: **8+ words** (word, translation, translationLang where non-default, pos, example, exampleTranslation), **4 useful phrases**, **4-line dialogue**, **1 reading passage** (title/text/translation). Original content only.
5. Unit ids: local to the level; use the next available number for the level (do **not** assume a global numbering scheme).

### Avoiding duplicate IDs

- Run a quick per-level id scan before committing (ids must be unique **within** a level). A committed validator (Section 11) will automate this.

### Avoiding duplicate vocabulary

- No duplicate `word` entries **within one unit** (the catalog dedupes these away silently — that wastes authored content).
- Cross-unit repeats are allowed **only** when the context/meaning is genuinely different; otherwise prefer a different word or a new example.
- After adding words, verify via `buildVocabularyCatalog` output that catalog ids are unique.

### Adding a new language

1. Create `curriculum-<lang>.ts` mirroring `curriculum-en.ts` (types import, helpers, `buildLanguagePack` call, `export const <LANG>_PACK`).
2. Optionally add a manual A0 unit in `curriculum-manual-<lang>.ts`.
3. Register metadata in `AVAILABLE_LANGUAGES` (`learn-data.ts`).
4. Add the language to the `LANGUAGES` registry in `App.tsx` (code, name, flag, dir, TTS code) and to UI strings (`STR`) if the UI should be localized.
5. Wire the pack into `loadLanguagePacks()`.

### Commits

- **One logical change per commit** (e.g., "feat: add structured English vocabulary terms", "docs: add application architecture philosophy v1").
- Curriculum batches: one commit per batch with a descriptive message (history shows this pattern).
- Run `pnpm run typecheck` **and** the Pages build (`PORT=3000 BASE_PATH=/Legacy-Code-Update/ pnpm --filter @workspace/lengoali run build`) before pushing.
- **Never commit** build output (`dist/`), `.local`, or local reports unless explicitly requested.
- Only stage files that belong to the current change; preserve unrelated user changes.

## 13. Design Decisions

### D1. Static SPA + GitHub Pages (vs server-rendered app)

- **Alternatives:** Next.js, SSR, a real backend.
- **Why:** free hosting, zero ops, instant load, easy collaboration via git. The core product (translation, curriculum, SRS) works entirely client-side.
- **Advantages:** cost, simplicity, portability, no auth/DB for the core loop.
- **Trade-offs:** no server-side translation (relies on unofficial endpoints), no user accounts/sync, curriculum is shipped in JS bundles (large but lazy-loaded).

### D2. Unofficial Google web endpoints for translation/TTS (vs official API)

- **Alternatives:** Google Cloud Translation API, LibreTranslate self-host, third-party SDKs.
- **Why:** zero keys, zero cost, supports 40+ languages, works on static hosting.
- **Advantages:** instant setup, rich `dt` data (definitions, synonyms, etymology).
- **Trade-offs:** unofficial contract, possible breakage/rate-limiting, no SLA. **Backend/API layer exists as scaffold but is not used.**

### D3. Seed + builder pattern for curriculum (vs fully hand-written lessons)

- **Alternatives:** hand-write every lesson; store content as JSON.
- **Why:** one unit seed produces two lessons, exercises, quiz, flashcards, review items — less authoring, consistent structure.
- **Advantages:** uniformity, authoring speed, type safety via TS.
- **Trade-offs:** generated exercises/quizzes are template-like; lessons are predictable (somewhat repetitive), and every unit must supply enough words/phrases to split into two lessons.

### D4. Per-level unit numbering (vs global unit ids)

- **Alternatives:** globally unique ids (`u54-a1`).
- **Why:** simplifies generation batches; each level's sequence is self-contained.
- **Advantages:** parallel authoring; no global registry to maintain.
- **Trade-offs:** ids repeat across levels — the UI and any tooling must always key on (level, unit); naive global dedup would delete legitimate units.

### D5. Repair layer (`curriculum-en-clean`) (vs manual fixes)

- **Alternatives:** hand-fix each contaminated record.
- **Why:** the contamination pattern was systematic (later generated batches accidentally used Finnish text in the English pack).
- **Advantages:** reproducible, self-healing for future batches, preserves legacy English records where clean.
- **Trade-offs:** heuristic risk (an edge case might invert the wrong record), and it introduces an indirection layer that future maintainers must understand.

### D6. Enrichment overlay (vs rewriting units)

- **Alternatives:** expand units directly.
- **Why:** enrich existing content without renumbering/restructuring; metadata-rich words can be added incrementally.
- **Advantages:** backwards-compatible, targeted.
- **Trade-offs:** enrichment must be merged by level+unit id — if a unit id changes, enrichment silently drops (a validator should catch orphaned enrichment keys).

### D7. Monorepo (pnpm workspaces) (vs single package)

- **Why:** the repo contains a product, a scaffold API, shared libs, and scripts; catalog pinning via `pnpm-workspace.yaml` keeps versions consistent; security settings (`minimumReleaseAge: 1440`) defend against supply-chain attacks.
- **Advantages:** central versioning, single lockfile, shared TS config.
- **Trade-offs:** workspace complexity; generated libraries (`api-client-react`, `api-zod`) currently have empty `generated/` dirs — the codegen pipeline is scaffold-only.

### D8. `localStorage` persistence (vs IndexedDB / server)

- **Why:** simplest possible persistence for a static app; no async APIs; survives reloads.
- **Advantages:** zero backend, trivial to debug, versioned keys allow migrations (`lengoali_saved_v4` migrated from v3).
- **Trade-offs:** ~5–10 MB limits, no cross-device sync, no structured queries, data loss on clearing site data. (Offline/sync are roadmap items.)

### D9. No URL router in the product (vs wouter/React Router)

- **Why:** the product is a set of tabs + drill-downs; deep links add little value for the current UX.
- **Trade-offs:** no shareable URLs per lesson; browser back button doesn't navigate app tabs. (`wouter` is installed but unused.)

## 14. Known Technical Debt

### Architecture

- `App.tsx` is a ~3,500-line monolith mixing reader, quiz, flashcards, saved-words, i18n, TTS, theme, and tab management. Refactoring into focused modules is the single highest-leverage cleanup.
- `curriculum-en.ts` / `curriculum-data.ts` duplicate builder helpers (to avoid circular imports); a shared builder module would remove the duplication.
- Unused workspace scaffolding: `api-server` (health-only), `lib/db` (empty schema), `api-client-react`/`api-zod` (empty generated dirs), `wouter` dependency, `mockup-sandbox`.
- shadcn/ui components vendored wholesale; many are unused (fine as boilerplate, but adds surface area).

### Curriculum

- Mixed translation languages in the English pack: base units default to Spanish; legacy `curriculum-en-more.ts` records are Arabic; repair layer infers per record. Learners may see inconsistent explanation languages across units.
- Per-level unit numbering can confuse tooling that assumes global ids.
- Some older units carry minimal metadata (no IPA/definition/synonyms).
- Legacy file name/comment brand "Lingolali" vs official "Lengoali" (documented in `docs/BRANDING_AUDIT_REPORT.md`; 13 occurrences to migrate).
- ~16.5k-line generated files are unwieldy to review in diffs (mitigated by the part-file pattern going forward).

### Vocabulary

- Metadata completeness is unenforced (optional fields).
- Duplicate detection only within a unit; cross-unit/level repeats are unmonitored (mostly intentional).
- No external frequency/CEFR corpus grounding for word selection.

### Performance

- Curriculum chunks are large (a ~16.5k-line TS file per language legacy set); parsing time on low-end devices is a minor concern; could be precompiled to JSON.
- Every word tap fires a network translation call (no local cache beyond browser HTTP cache).
- `Math.random()` shuffle in generated quizzes is not seeded (testability).

### Maintainability

- No tests at all.
- No committed validator/statistics tool; audits are ephemeral scripts.
- No contributing guide beyond this document; generated-file discipline depends on convention.

## 15. Future Roadmap (recommended order)

1. **Curriculum Validator (first).** Before adding more words, build the validator from Section 11 (structural + duplicates + metadata coverage + language sanity). This makes every later step safe. *Highest educational value & software quality return.*
2. **Metadata enrichment drive.** Fill IPA/definition/synonyms/collocations/word family/tags on existing English words via the enrichment bank — increases SRS and reader quality without new units.
3. **English curriculum to 5,000+ words.** Add part files `part18+` following the rules; the validator gates each batch.
4. **Finnish continuation.** Mirror the English pipeline (clean + enrich + parts) for Finnish.
5. **New languages.** The architecture supports adding packs; explanation-lang UI (ar/es/fi/fr/en) already exists.
6. **Offline support (PWA + service worker).** Cache the app shell and curriculum chunks; localStorage already gives offline progress.
7. **Synchronization.** Move saved words/progress to IndexedDB with optional account-based sync (the scaffold `api-server`/`lib/db` becomes relevant here).
8. **AI features.** AI-assisted example generation, cloze exercises, personalized SRS tuning, translation quality checks — all additive to the existing data model.

**Before 5,000 words:** validator + metadata completeness goals must land first, otherwise volume will outpace quality.

## 16. AI Development Guide

### How to understand the project

1. Start from `learn-data.ts` — all types radiate from it (`LanguagePack → Level → Unit → Lesson → VocabularyItem`, etc.).
2. Read the builder functions in `curriculum-en.ts` (lines ~59–300) — they define how seeds become lessons and are the heart of the architecture.
3. Trace one unit end-to-end: seed → `buildLesson` → rendered in `LearnCenter.tsx` → flattened in `vocabulary-data.ts` → reviewed in `LearnWordVocab.tsx`.
4. Read the package scripts in the root `package.json` and `artifacts/lengoali/package.json` before running anything.

### What you must NEVER change

- `main.tsx` bootstrapping and the `index.css` global styles/Tailwind foundation.
- `vite.config.ts` (requires `PORT` and `BASE_PATH`; `server.hmr` constraints; changing it breaks the build and preview).
- `learn-data.ts` type contracts in breaking ways without updating every consumer.
- Generated files (`curriculum-*-more.ts`) — never hand-edit; regenerate or repair through code.
- `.github/workflows/pages.yml` build contract (`dist/public`, `BASE_PATH=/Legacy-Code-Update/`).
- Env/secret files (`.env*`).

### How to safely extend

- Prefer **additive** changes: new part files, new enrichment entries, new components.
- When adding a batch, follow the exact shape of an existing part file (`curriculum-en-part16.ts` is a clean recent example).
- If you must refactor exported symbols (functions/types), update all references (use code search for each symbol).
- Keep unit ids local per level; key everything on (level, unitId).
- Add translations with an explicit `translationLang`; keep target-language text out of `translation`/`exampleTranslation` (that is exactly what the repair layer exists to fix).

### Preserving compatibility

- Run `pnpm run typecheck` and the Pages build (`PORT=3000 BASE_PATH=/Legacy-Code-Update/ pnpm --filter @workspace/lengoali run build`) before finishing.
- Don't bump React/Vite/Tailwind versions casually — the workspace catalog pins them; `react`/`react-dom` are pinned to exact versions.
- New `localStorage` keys should be versioned and ship with a migration from the previous key (pattern: `lengoali_saved_v4` ← v3).
- Keep changes minimal and reviewed: this codebase favors simple, typed, additive evolution over rewrites.

## 17. Philosophy Summary

Lengoali is a **free, client-side language-learning platform** built on a simple and deliberately boring stack — React + Vite + TypeScript on GitHub Pages — because the product idea is about *content and method*, not infrastructure.

Its soul is **translation-first reading**: make any real text instantly understandable, let learners save what they touch, and reinforce it with spaced repetition, quizzes, and flashcards. Around that, a **typed, generated CEFR curriculum** (A0–C2, two languages, hundreds of units) provides structure for those who want a course, not just a reader.

The engineering philosophy is *additive and conventional*: seed data + builders produce uniform lessons; content grows in separate part files that merge at build time; a repair layer keeps generated content honest; a flat vocabulary catalog powers a deterministic SRS; everything a learner does lives in versioned `localStorage`. Complexity is deferred — no router, no backend, no accounts — until the roadmap (validator → metadata → 5,000 words → new languages → offline/sync/AI) justifies it.

The next maintainer's duty is clear: **quality before quantity.** Add the validator, enforce metadata completeness, then grow the curriculum with discipline — always keying units by (level, id), never editing generated files, and always running the typecheck + Pages build before pushing.
